## Priority 2 — recommendations for #17 ingestion

- **Reading payload.** Use version 1, immutable UUID `event_id`, registered `collector_id` and `device_id`, registered `measurement_scope` (`household` or `appliance`) and `source_kind` (`simulated` or `physical_device`), plus `sample_run_id` for simulated readings and null for physical readings. Use offset-bearing RFC 3339 `device_measured_at` (nullable) and `collected_at`, with `timestamp_basis` selecting a trusted device measurement or collector observation. Store server `received_at` once and keep all three times distinct. Use finite active import `power_w` and cumulative `energy_import_total_kwh`, both nonnegative and either nullable when the other is present. Require integer `counter_epoch` from zero, `quality_flags` and nullable `reset_evidence`. Use `partial_measurement` when a supported measurement is absent. Reject untrusted observation times, unsupported measurements and explicit export fields with per-event reasons. Do not infer import from net readings or clamp negative values. Report export support and physical plausibility limits as adapter decisions under #4.
- **Epochs and reset.** Start each device/run at epoch 0. To open exactly the next epoch, require `counter_reset` and `reset_evidence: {kind, previous_event_id}` on the first new reading. The prior ID must reference the newest accepted counter in the preceding epoch of the same device/run. The new observation must follow it and provide a lower counter. Verify `simulated_reset` against the registered run’s reset schedule. A `device_reset` marker requires approved device-model corroboration under #4. Unexpected decreases or skipped epochs are rejected pending evidence. No cross-epoch delta is available. A verified new epoch starts a baseline and the next compatible counter can establish consumption. A reset recovered above the old value remains unsupported until model-specific evidence is agreed.
- **Statuses and limits.** Use 1–1,000 events and a 1 MiB UTF-8 request body limit. Start collectors at 100 events per send and split larger imports. Parse a valid versioned envelope before applying per-event validation, so malformed individual events can have a 200 response with mixed outcomes. Return results in input order, identified by zero-based `eventIndex` plus `eventId` where syntactically valid. Outcomes are `accepted`, `already_stored` or `rejected`, with a stable rejection code and optional explanatory message. Use 400 for malformed JSON, 422 for an invalid envelope or count, 413 for an oversized body, 401 for invalid credential, 403 for endpoint-wide disallowed scope, 429 for throttling and 503 for a temporary commit failure. A device outside the authorized assignment is an individual `device_unavailable` rejection. Any request-level error gives no per-event acknowledgements.
- **Retry and concurrency.** Uniqueness is `(registered collector ID, event_id)`. After checking request scope and event identity, look up that key. Compare the immutable event, disregarding object key order and including all measurement/timestamp/metadata fields. Identical retry returns `already_stored` with the original `receivedAt`. Changed duplicate returns `event_conflict` with no overwrite. A different event ID at an occupied device/run observation time returns `observation_conflict`. Resolve occupied keys atomically with committed data, including concurrent deliveries. Evaluate same-batch entries in input order and return accepted outcomes only after one transaction commits. On commit failure the collector can retry its original input.
- **Clock and delayed arrival.** Allow up to 120 s future skew against server UTC for physical events or the authorized scenario clock for simulated observations. A newly inserted late event may be at most 30 days behind the newest accepted observation in that device/run; ordered backfill can start earlier. Check known IDs before time-window revalidation so an already accepted retry remains safe. A delayed insert must fit both neighbors' counters and adjacent epoch boundaries. Readings that would invalidate an accepted reset reference or split the cross-reset interval require review. Derive totals in observation order, replace the affected neighboring deltas transactionally, and invalidate dependent bucket/cost/forecast/comparison outputs. Keep freshness based on the newest observation and receipt on first durable acceptance.
- **Coverage and queries.** A same-epoch pair with nondecreasing counters establishes energy over its exact half-open interval. Assign deltas to buckets only where they fit wholly; a wholly covered broader period can use the total while finer buckets remain unavailable. Missing boundaries, unresolved reset or uncertain time prevent claiming complete coverage. Do not extrapolate an interval or divide a known total across unsupported buckets. Preserve valid zero and display partial values with coverage/explanation. Recommend default 100 and maximum 1,000 readings, stable order by `(observedAt,readingId)` and a cursor that resumes strictly after the last key, bound to household/filter. Recommend maximum 31 days for hourly and 366 days for daily consumption queries, with explicit 422 for invalid or reversed ranges.

Use these proposed codes for `rejected` events:

| Code | Condition |
|---|---|
| `invalid_event` | Event shape or identity is invalid. |
| `device_unavailable` | Device and collector ownership, assignment, source or scope do not match the registration. |
| `invalid_reading_value` | Both measurements are absent, or a supplied measure is negative, non-finite or physically invalid under an agreed adapter rule. |
| `unsupported_measurement` | The input includes export data, a replacement for imported active energy, or other unsupported measurement fields or units. |
| `invalid_observation_time` | The observation has an invalid, untrusted or out-of-tolerance timestamp. |
| `outside_late_window` | A new observation is more than 30 days behind that device/run’s latest accepted observation. |
| `reset_evidence_required` | A counter decrease or epoch transition lacks accepted evidence, or a late event would invalidate a recorded transition. |
| `event_conflict` | A committed event ID is reused with different input. |
| `observation_conflict` | A different event already occupies the same device/run observation time. |

Worked inputs and outcomes are in [the ingestion examples](../api/examples/v0.1/ingestion/). Review exact fields, codes, retry order, reset proof, window, bucket reasons and pagination with Ahmed and review freshness/coverage display with Miray before relying on them.

**#17 acceptance after confirmation** — authorized devices can store and retrieve readings across restart, foreign devices are rejected, mixed batches commit only accepted rows, retries preserve counts, changed duplicates preserve original values, resets add no negative delta, and delayed input changes only the supported buckets while preserving established totals. The [scenario definitions](scenario-definitions.md) give reproducible cases.

## Priority 3 — recommendations for #18 simulation

Use 60 s historical intervals, 10 s live reporting and 60 s heartbeat. Carry forward provisional stale at 30 s and collector unreachable at 180 s. Use one scenario clock for reporting, freshness and replay, with 1× normal speed and a proposed 10× replay option. Freeze completed replay at its cutoff after committed acknowledgements and expose completion as a distinct state. A deterministic seed, scenario version, run ID and range reproduce input. A fresh run gets a new namespace. Use the real authenticated ingestion pipeline and scope reset to an explicitly named, owner-confirmed isolated synthetic run. See [scenario definitions](scenario-definitions.md).

**#18 acceptance after confirmation** — generate history and stream it through the real ingestion interface, read persisted results after restart, reproduce totals/retries within a run, keep synthetic provenance and exercise missing data, disconnect, recovery and completed-replay states.
